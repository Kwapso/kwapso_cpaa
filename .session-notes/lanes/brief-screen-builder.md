# Lane brief: a screen-assembly sandbox, built from the kit and nothing else

You are a build lane on **the Kwapso System** (`Kwapso/kwapso_system`). The owner wants a
desktop-only, Glide-like page where he can drag kit parts onto a canvas, configure them,
see them with dummy data at desktop and phone width, and press Save to download a file he
hands back to a developer or an agent.

## THE ONE RULE THAT OVERRIDES EVERYTHING

**The owner, verbatim: "Don't magically add configurations on the components or collections
that Aurora has not put in the UI/UX kit. You should only show me what is there as of this
moment, live."**

So every option the tool offers must be DERIVED from the kit's own source. Not
hand-written, not remembered, not "sensible defaults". If a component has three variants in
its `cva` block, the tool offers exactly those three, spelled exactly that way. If a
component has no variants, the tool offers none and says so.

A hand-maintained list of options is a FAILURE of this brief even if it happens to be
accurate today, because it will drift the first time Aurora tags a version.

## What is actually there — measured 4 Sep 2026

- `shared/ui/components/` — **116 component files**, of which **40 declare variants via
  `cva()`**. Those 40 are where real configurable appearance lives. Example:
  `shared/ui/components/button/button.tsx:64-170` has `variant:` and `size:` with their
  values AND their Tailwind class strings inline.
- `shared/ui/compositions/` — 47 files: 2 templates (`collection-screen`, `detail-screen`)
  and 19 whole screens. These are ALREADY-BUILT screens. The owner's interest is in what
  Aurora has NOT already built, so treat compositions as reference, not as raw material.
- `shared/ui/foundations/tokens/tokens.css` — **2,301 lines, 546 custom properties.** This
  is the real design system and it is inlinable.
- **There is no manifest, no index, and no stories file.** Nothing enumerates the kit. The
  catalogue must be derived by parsing source.

## Shape — two pieces, in this order

### 1. A generator script (`scripts/build-kit-catalogue.mjs`)

Reads `shared/ui/` off disk and emits a JSON catalogue: for each component, its name, file,
whether it has variants, and for each variant group its exact option names **and the
Tailwind class string each one applies**. Take the class strings from the source; do not
write CSS of your own for a component that has some.

`shared/ui/` is hash-pinned and READ-ONLY. Read it; never edit it. Re-running this script
after `scripts/sync-design.mjs` pulls a new kit tag is what keeps the tool current — that
is the honest meaning of "live", and the tool must print the kit tag from
`shared/ui/VERSION.json` so the owner can always see which version he is looking at.

### 2. The builder page itself

Standalone HTML. Inline `tokens.css` so colours, radii and spacing are genuinely the kit's.
Load Tailwind from `https://cdn.tailwindcss.com` so the kit's own class strings resolve.

- **A palette** of every catalogued part, grouped as the kit groups them on disk.
- **A canvas** — drag parts on, reorder, remove. Vertical stacking is enough; the app has
  no free x/y placement and inventing one would violate the rule above.
- **A properties panel** showing ONLY that part's real options, from the catalogue.
- **Dummy data by default**, always. Every part appears filled — a list has rows, a chart
  has bars, a card has a title. Nothing renders empty.
- **Desktop and phone toggle**, side by side or switchable. Desktop-only tool; the phone
  view is a preview inside it.
- **Save** downloads a JSON file describing the screen plus a readable summary. No syncing,
  no server, no persistence beyond the download.

## Say what you cannot do, in the tool itself

Three things the owner asked for that the kit or the browser will not give. Do not silently
omit them — put a short, plain line in the tool where he would look for each:

1. **It cannot fetch Aurora's GitHub live.** The kit repo is private and a browser page
   cannot read it. The catalogue is regenerated by one command against the pinned copy.
   Show the kit tag and the generation date on screen.
2. **Backgrounds and free placement are not kit options.** The app has one page width per
   door, two corner radii and a closed colour palette, all machine-checked. If you offer a
   background control at all, mark it plainly as a sandbox control that does not exist in
   the app — the owner explicitly wants to be able to SHOW what he means, so a clearly
   labelled not-shippable control is better than its absence. Never present it as a kit
   option.
3. **76 of 116 parts have no variants.** Show them, with "no options" rather than inventing
   any.

## Constraints

- **Never edit `shared/ui/`** — hash-pinned, the build goes red.
- `npm run check` green before you finish, read by EXIT CODE. Baseline: **3,967 tests**.
- Every Cloudflare command takes the `cf-exec` prefix. Never run `scripts/i18n-translate.mjs`.
- This tool is a developer tool, not a shipped screen. Keep it out of the front doors'
  import closure so it does not drag the i18n and screen-width laws onto itself — a
  standalone file under `tools/` or `verify/`, not under `web/`.
- Do not deploy. Branch, PR, and report back.
