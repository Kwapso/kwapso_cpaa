clearly-marked placeholder in `web/components/temp/`, list it HERE, and the
library absorbs it later (built + tested there, then re-imported here and the

| 14 | `web-embed` **default sandbox pairs `allow-scripts` with `allow-same-origin`** |, (host now pre-checks the URL with `safeSrc`) | `WebEmbed`'s default is `"allow-scripts allow-same-origin allow-popups allow-forms allow-presentation"`. It's the right default for a YouTube/maps embed and the wrong one for an arbitrary link a member typed. Proper fix: an explicit `trust: "embed" \| "unknown"` (or default WITHOUT `allow-same-origin`, opted in per embed), so the untrusted case is the easy one. | 15 | `screen-renderer` **doesn't pass the frame's `serverSide` seam through** | `web/components/paged-find.tsx` (host-composed, not a temp fork) | `CollectionFrame` already has the right seam, `serverSide` + `onQueryChange`, "the frame stops filtering in memory and emits the query so an app can refetch". `ScreenRenderer` renders that frame from a recipe and passes neither, so a recipe-driven screen cannot use it. That is a real gap, because on a PAGED collection (R14) in-memory search is a lie: it answers about page one under a badge counting everything. Brimba's side is done, the recipe turns the frame's box off and the host draws its own find bar over the door (SEARCH.md layer 2), but the facets on four paged screens are still the frame's, so they still narrow the loaded page. Proper fix: `ScreenRenderer` accepts `serverSide` + `onQueryChange` and forwards them to its `CollectionFrame`, so a paged recipe declares its search/filters once and the host answers them from the door. | **flag for the library** |
| 16 | `screen-renderer` **maps a row to a title and a subtitle, with no leading slot** | none, the mark is simply absent on an engine list (`web/lib/type-marks.ts` carries the read side, ready for the day it lands) | UI-CONVENTIONS §5 (amended 17 Aug 2026) allows a TYPE MARK, one glyph in the slot a lucide icon would take, and CHECKLIST 11.8 asks for one on every collection. The library `List` already HAS the slot, `item.leading` (`registry/collections/list/list.tsx:19,94`), and the host uses it directly on the sprints overview, where the mark shows today. But `ScreenRenderer`'s `renderList` builds each row as `{ id, title, subtitle }` and passes no `leading`, so a recipe-driven collection cannot carry one, which is every ticket, story and account list plus the sprints **All** tab. The workaround would be to put the glyph inside the title string, and that is the ONE shape §5 refuses (a pictograph inside a sentence), so nothing is done host-side and the mark is simply absent there, the WORD still carries the meaning on its own. Proper fix, one line: `renderList` reads an optional `leading` column off the row (as it already reads `fields[0]` for the title) and passes it to `List`. | **flag for the library** |
| 17 | `notes` **takes no `id` and forwards no ARIA, so its `Field` label points at nothing** | none — the visible label still sits above the editor, so a sighted person reads it; a screen-reader user hears an unlabelled edit box | The library `Notes` renders a toolbar plus a `contentEditable` div and accepts only `defaultValue` / `onChange` / `placeholder` / `className`. There is no host workaround: wrapping it in a `<div id>` does not help, because a `<label for>` only binds to a LABELABLE element and a div is not one. Proper fix, small: `Notes` accepts `id` and `aria-label` (or `aria-labelledby`) and puts them on the editable div, which should also carry `role="textbox"` and `aria-multiline`. A `disabled` prop would close the other half of the same gap — every form here passes `disabled={busy}` to its other inputs and cannot to this one, so the editor stays typable while a save is in flight. | **flag for the library** |
| 18 | `tabs` (`TabsView`) **resolves `icon` as a lucide NAME, so a type MARK cannot sit in a tab** | none — the tab shows its WORD alone | `TabsConfig.tabs[].icon` is typed `string` and rendered `<DynamicIcon name={t.icon as IconName} fallback={() => null} />` (`registry/primitives/tabs/tabs.tsx:144,215`), so anything that is not a lucide name draws nothing at all. | 19 | `collection-frame` / `screen-renderer` **empty state is a bare string** | none — the host's OWN empty states carry a glyph (`screen-bits.tsx`, `pulse.tsx`); a RECIPE-driven one cannot | `CollectionConfig.emptyText` is a `string`, so an engine-rendered list with no rows shows one grey sentence in the middle of a card. | 22 | `calendar-view` **draws records nobody can open, and hides some behind dead text** | `web/components/record-calendar.tsx` (`RecordCalendar`, host-composed from `Button` + `List` + `ToggleGroup` + `Dialog`, not a temp fork) | `CalendarView` renders each event as a plain `<div key={idx}>` and exposes **no** click prop of any kind — its whole config is `dateField` / `titleField` / `accentField` / `weekStartsOn` / `maxPerDay`, and the only `onClick`s in the file are Today / previous / next. So a task on the grid is a PICTURE of a task: no keyboard focus, no pointer target, no way to its detail screen. `+N more` is a second plain `<div>`, which is worse than silence — it names six records and offers no gesture that reaches any of them. There is no host workaround: `titleField` is read as `String(ev[field])`, so a node cannot be passed in, and delegating a click from a wrapper would mean identifying the record from the DOM. Reported by the owner, 18 Aug 2026 ("all detail screens should be clickable and accessible if there are records displaying on the calendar"). **The change, exactly:** `CalendarViewProps` gains `onEventClick?: (row: T) => void` and `onOverflowClick?: (day: string, rows: T[]) => void`; when the first is given the event `<div>` becomes a `<button type="button">` with the row's title as its accessible name, and when the second is given so does the `+N more` line (defaulting, if a library owner prefers one prop, to `onEventClick` on both, since "open the day" is a host decision). | 17 | `choice` **is the library's searchable picker and it cannot ask a door** | `web/components/record-picker.tsx` (host-composed from `Popover` + `Command`, not a temp fork) | The library ALREADY ships the searchable combobox: `Choice` (`registry/primitives/choice/choice.tsx`), `display: "dropdown"` + `searchable: true`, built from `Popover` + `Command` (cmdk) with a `modal` prop for living inside a dialog. It is the right control for every picker in this app over a BOUNDED list, and nothing here beats it. What it cannot do is ask a SERVER: it owns its search text in local state (`const [query, setQuery]`), never emits it, and hands it to cmdk's own in-memory filter — so on a `GROWING_COLLECTIONS` list (R14) it would search the loaded page and answer "no options found" about everything past the cursor, confidently. That is precisely the defect this repo already hit on the accounts picker and the one `PagedFind` exists for on list screens. So the host composed the same two primitives with the search wired to the door instead. Proper fix, the same shape `CollectionFrame` already has (see #15): an optional `onSearch?: (query: string) => void` + `serverSide?: boolean` on `ChoiceConfig`, which turns cmdk's filter off (`<Command shouldFilter={false}>`) and emits the debounced query, plus a `loading?: boolean` and an `emptyText` that can differ while a search is in flight (saying "nothing matched" before the door has answered is the same lie in a smaller box). With that, `record-picker.tsx` collapses onto `Choice` and this row closes. NOT BLOCKING: the composition works today and uses only shipped primitives. | **flag for the library** |

| 22 | `collection` **sorts by the rendered TEXT, and a `data-table` header sorts NOTHING** | `shared/web/format.ts` `formatDateSortable` (the values that get compared are spelled so lexical order is real order) + `web/components/paged-find.tsx` (a door-side sort control beside the search box) + `web/components/record-table.tsx` (the table itself, host-composed from `CollectionFrame` + the `Table` primitives, not a temp fork) | TWO gaps in one row, because they are one control. **(a) The comparison.** `selectRows` step 4 is `typeof av === "number" && typeof bv === "number" ? av - bv : String(av).localeCompare(String(bv))` (`lib/collection.ts:105`), so a column holding a formatted date ("14 Apr 2025"), a duration, money as text or a padded number sorts ALPHABETICALLY — April before January — and does it silently, because the rows move and the control looks like it worked. Proper fix: a per-column `sortType` (`"text" \| "number" \| "date"`), or an optional `sortKey?: (row) => string \| number` on `DataTableColumn` so a column can DISPLAY one thing and COMPARE another. `DataTable` already knows each column's `type` (`"text" \| "number" \| "badge" \| "date"`) and simply does not use it for the compare, so most of the answer is already declared. Host side is done for the three columns that were wrong, at the cost of showing "2026-04-14" where a warm date belongs. **(b) The coverage — and the sentence above it was WRONG, which is the point.** This row originally said `DataTable` "feeds that choice into the frame's in-memory pipeline", so a header ordered the loaded page. It does not. **`DataTable`'s header sorts nothing at all**, and did not on either table: it keeps the choice in its own state and passes it down as `CollectionFrame`'s `config.sortBy`, and the frame seeds its sort from that prop ONCE at mount (`collection-frame.tsx:83`, `React.useState(config.sortBy)`) and orders by its own state ever after. So the header wrote to a value nobody reads, on every column, while its ARROW — the header's own state — moved correctly. Reported on the deployed build within hours of this row being written. `screen-renderer` hard-codes `sortable: true` on every column of a `display: "table"` recipe (`screen-renderer.tsx:542`), so there is no host workaround through the engine: the affordance cannot be turned off from here and cannot be made to work from here. **The change, exactly:** the frame keeps the prop and the state in step (`React.useEffect(() => { setSortBy(config.sortBy); setSortDir(config.sortDir) }, [config.sortBy, config.sortDir])`, the same two lines `SearchInput` already runs for its `value`) — that alone makes every existing `DataTable` header work. Then, for the paged case, `DataTable` accepts `serverSide` + `onSortChange` and `ScreenRenderer` forwards them (#15's sentence, said about sorting), so a header can ask the door instead of the array. Host side is done and does not wait on either: `web/components/record-table.tsx` composes `CollectionFrame` with headers the host owns, ordering a bounded collection in the browser and a paged one at its door. **NOT BLOCKING**, and it retires the moment the frame syncs — `web/test/table-header-sorts.test.tsx` watches the library for exactly that line and goes red when it changes. | **flag for the library** |

**One placeholder is not in `web/components/temp/`, and it needs saying.**

inside one of them. So it now sits in the most permanent folder in the repo with

`web/components/temp/`.
